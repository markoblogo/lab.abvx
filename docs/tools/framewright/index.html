Reproduce the example

Task: introduce Framewright in a 30-second horizontal film.

Selected chain: authored Remotion scenes + original locally synthesized music → native MP4 and PNG still.

Result: watch the Framewright film.

Checked: H264 1920×1080, 30 fps, 900 frames, stereo AAC, native PNG and sampled encoded transitions. Human listening and audience performance are separate.

Open reference project: authorised assets, pinned dependencies, exact agent request, commands and output checks. Pilot elapsed time and compute cost were not retained; no speed or cost benchmark is claimed.

Choose tools by scene and layer

  1. Software launch. Brag full + Hyperframes for a short introduction grounded in the working project.
  2. Narrated book trailer. Existing artwork + local Kokoro narration + sound-layer checks for the final encoded file.
  3. Live React interface. Flute camera/focus around existing components; FFmpeg can add music and extract a thumbnail where the portable snapshot failed.
  4. Authored motion graphics. Remotion for frame-based typography, native audio and stills; Anatomy can provide object SVG assets within its prototype scope.
  5. Common finish. A film can combine tools per block and layer. Declare timing, canvas, colour/alpha and sound handoffs; validate the assembled file.

Eight-tool capability matrix distinguishes tested, documented, failed and unknown features. Style is an authoring direction, not a fixed engine limit. The offline JSON planner proposes combinations; new chains still need integration tests.

Eight exports; routing evaluation still pending

Anatomy's visual prototype passed, but its combined sound experiment failed QA. Historical reconstruction and calibrated physics remain untested.

Framewright is a methods library, not a hosted renderer. Automated QA, human listening, user preference, publication and audience performance are separate claims.
